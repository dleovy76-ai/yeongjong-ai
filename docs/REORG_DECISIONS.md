# 재정비 검토 결정사항 (2026-08-26)

## 배경

외부 AI(Gemini)가 제안한 확장 pitch 문서(① 제안 배경/핵심가치 ② 멀티 에이전트 구성 ③ 대시보드 UX
④ 요금 체계 ⑤ 도입 프로세스 ⑥ 기술 아키텍처+코드)를 실제 코드(`backend/`, `frontend/`)와
섹션별로 하나씩 대조 검토했다. 별도로 현재 저장소 구조 전체를 `docs/MASTER_PLAN.md`,
`CLAUDE.md` 기준으로도 감사했다.

**결론: 코드/구조는 재작성이 필요 없다.** 마스터플랜의 원칙(§29 지어내지 않기, §18 attribution,
§4 LLM abstraction, §52/§53 Agent/Tool 구조)이 실제 코드에 그대로 살아 있고, MVP 체크리스트
(§57) 17개 중 사실상 전부 구현되어 있다. Chef AI를 Customer AI로 통합한 것처럼 계획과 다른
지점도 전부 이유가 코드 주석에 문서화되어 있고 타당했다.

**진짜 문제는 기능이 아니라 검증이다.** 지금까지 만든 모든 것 — Manager/Customer/Info/Expansion
AI, 쿠폰, 예약, 성과 대시보드, 파트너 그래프, 관리자 화면 — 은 마스터플랜 부록이 강조하는 핵심
루프(방문객 질문 → AI 추천 → 쿠폰/예약 → 실제 방문 → 실제 매출 → 사장님 재사용 → 다른 업체 소개)를
"돌릴 준비"였을 뿐, 이 루프가 실제 사람으로 한 번도 검증된 적이 없다(파일럿 업체 0곳).

## 결정 1 — pitch 문구는 실제 구현 기준으로 다시 쓴다 (기능을 pitch에 맞추지 않는다)

Gemini pitch가 설명한 것 중 실제로 존재하는 건 CS 상담 자동화(Customer AI), 예약/쿠폰 자동화,
지역 추천(Info AI), 파트너 네트워크(Expansion AI)뿐이다. Supervisor 라우팅, 실시간 데이터
동기화 에이전트, 마케팅/리뷰 자동화 에이전트, CRM/재고 수요예측, 하이브리드 요금제 — 전부 코드
어디에도 없다(각 섹션별 근거는 아래 "검토 상세" 참고).

파일럿도 아직 안 돌려본 상태에서 기능부터 없는 것들로 늘리면, 정작 검증해야 할 핵심 루프 확인이
계속 미뤄진다. pitch 문구를 고치는 게 코드를 새로 만드는 것보다 훨씬 싸고, 지금 있는 기능만으로도
가치 제안(본업 방해하는 반복 업무를 AI가 덜어준다)은 충분히 성립한다.

(pitch 문서 자체는 이 저장소 안에서 발견되지 않았다 — 랜딩 페이지 문구(`frontend/app/page.tsx`)는
이미 실제 기능 기준으로 정직하게 쓰여 있어 손댈 필요 없어 보인다. 별도 외부 자료라면 오너가 직접
관리)

## 결정 2 — 지금 가장 중요한 건 실제 파일럿 실행

다음 작업 우선순위는 기능 추가가 아니라, 실제 업체 1~2곳을 붙여서 핵심 루프를 실제로 돌려보는
것이다.

## 작업 우선순위

### P0 — 파일럿 준비

1. `docs/`에 지금 실제로 있는 기능만으로 파일럿 온보딩 절차 문서화. Gemini pitch ⑤번 섹션의
   3단계 뼈대(기본설정 1~2일 → 시범운영 1주 → 정식가동)는 구조가 괜찮으니 유지하되, 리뷰관리/
   마케팅/CRM 활성화 같은 없는 기능 언급은 전부 빼고 다시 쓴다. `backend/scripts/seed_demo_pilot.py`가
   있으면 참고/재사용.
2. `frontend/app/businesses/[id]/page.tsx`의 예약 경로 중복 정리 방안 검토 — 수동 "예약
   요청하기" 폼과 AI 대화형 예약 확인 카드가 동시에 노출되어, 실제 방문객이 헷갈릴 수 있다
   (설계 의도는 `docs/P1-6_CONVERSATIONAL_RESERVATION.md`에 문서화돼 있으니 먼저 읽을 것).
3. 온보딩 완료 시 "우리 가게 AI가 이제 준비됐다"는 체감 순간 추가 검토 — 지금은 업체+메뉴 등록만
   하면 화면 전환 없이 바로 대시보드로 넘어가, 완성 시점이 사장님에게 명확히 안 보인다.

### P1 — 저비용 개선 (파일럿 시작과 함께 넣을 만함)

4. `services/llm/gemini_provider.py`(또는 `BaseAgent._call_llm`)에 타임아웃 + 폴백 처리
   추가. 지금은 없어서, Gemini API가 느려지거나 멈추면 사용자가 무한정 기다리게 될 수 있다.
5. 채팅 응답에 가벼운 피드백(예: 👍/👎) 추가 — `AiInteraction`에 컬럼 하나 정도의 최소 스키마
   변경으로 가능. 지금 없는 "응대 해결률/만족도" 지표의 최소 버전.

### P2 — 데이터 쌓이면 착수 (지금은 설계 메모만, 구현은 나중)

6. 재방문 주기 분석 — `CouponIssue.customer_user_id`/`Reservation.customer_user_id`가 이미
   있어서 새 인프라 없이 계산 가능하다. 다만 로그인 손님 자체가 아직 없으니, 파일럿으로 실사용자가
   생기기 전까지는 우선순위 낮음.

### 보류/폐기 (이번 재정비에서 하지 않는다 — 이유 포함)

- **Supervisor 라우팅 에이전트**: 에이전트 4개 규모에서는 과설계 (마스터플랜 §59 "Do not
  overengineer"). 에이전트 수가 실제로 늘어났을 때 재검토.
- **실시간 데이터 동기화 에이전트**: 네이버 API가 영업시간/메뉴 변경 데이터를 애초에 제공하지
  않는다 — `services/external/naver_local_api.py` 상단 주석에 "리뷰 수/영업시간/메뉴는 절대
  긁어오거나 저장하지 않는다"고 이미 명시돼 있다. 방식을 바꾸는 게 아니라 아이디어 자체를 접어야
  한다.
- **마케팅/리뷰 자동화 에이전트**: 파일럿으로 핵심 루프 검증 이후 로드맵.
- **CRM 재고 수요예측**: 실제 재고/POS 데이터 연동이 전제인데 아직 없음. 로드맵.
- **하이브리드 요금제(정액+크레딧) 설계**: 실사용 원가/사용 패턴 데이터가 하나도 없는 상태라
  지금 설계해봐야 근거가 없다. 마스터플랜 §37도 "가격은 실제 고객 인터뷰와 비용구조 검증 후
  확정"이라고 명시.
- **Gemini가 제시한 예시 코드(FastAPI/asyncio Supervisor 샘플) 자체**: 채택하지 않는다. LLM
  호출 없이 키워드 매칭으로 동작하는 목업이고, 상태 저장이 전부 인메모리 dict라 서버 재시작/
  다중 인스턴스에서 깨진다. 유일하게 건질 아이디어는 위 P1-4(타임아웃/폴백)뿐이다.

## 작업 방식

`CLAUDE.md` / 마스터플랜 §58 그대로 따른다: 항목 하나씩 **PLAN → FILES TO CHANGE → IMPLEMENT
→ TEST → VERIFY → REPORT**로 진행하고, 각 단계 끝에 구현한 기능/변경 파일/DB 변경/API 변경/
테스트 결과/남은 문제/다음 단계를 보고한다. 한 번에 여러 항목을 묶어서 처리하지 않는다.
